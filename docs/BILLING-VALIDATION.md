**2026-11-02 更新：下文为修复前的历史报告。** 已修复整批保存、失败回滚、异常中止、005 月度防重及并发防重；本次计算测试 20/20、真实 MySQL 事务测试 12/12、SQL 隔离检查 4/4 通过，真实本地 HTTP 正常出账及提交中断重试均确认一张汇总、一条明细、零孤立明细。详见 [业务修复记录](BUSINESS-REPAIRS.md)。自动任务仍未启用，历史异常数据未自动改写。

当前生成流程：计算整批明细 → 事务内锁定收费配置并复查账期 → 同一事务保存汇总和全部明细 → 提交成功后供后台查看/手动推送。下文“先逐条保存明细，再保存汇总”的流程已被替换。

验证日期：2026-10-26。客户尚未确定正式出账日，明确要求先验证现有逻辑。本轮交付为可重复运行的验证工具与结果报告，未实施新的账期规则或出账修复。

## 结论

原有账单生成逻辑可以复用：月费、面积计费、缴费周期、预付/后付、累计欠费、业主与房屋定位均有可用基础，正常本地出账及同一周期顺序重试验证通过。

但当前不能直接据此启用每月自动出账和自动通知。异常恢复、并发防重和不完整账单处理存在已复现的问题；其中“账单头请求中断，重试后遗留孤立明细”已在实际本地服务和独立数据库上复现。

完整脱敏结果见 [验证结果 JSON](validation/2026-10-26-billing-results.json)。

## 实际采用的流程

数据库中的账单任务模板 `1002` 指向 `generateBillProTemplate`。`GenerateBillTemplate` 是另一份旧实现，不是当前账单任务指向的实现。

```mermaid
flowchart LR
    A[收费项目及房屋关联费用] --> B[按周期和缴费到期日计算欠费]
    B --> C[逐条保存 bill_owe_fee 明细]
    C --> D[保存 bill 汇总并切换当前账单]
    D --> E[后台查看与手动推送]
    E --> F[微信受理通知]
```

这套逻辑生成的是“某个收费项本次的欠费快照”，并不直接等同于一笔仅含自然月费用的新应收订单。

- 收费项 `bill_type=002`：按月出账。
- 费用记录 `fee_flag=1003006`：周期性费用；`2006012` 为一次性费用。
- `payment_cycle` 决定缴费周期；`payment_cd=1200` 为预付，其他值走后付分支。
- 收费开始日、已缴费到期日及收费项结束日共同决定目标到期日和累计欠费月数。
- 明细 `amount_owed` 为一个缴费周期的金额，`bill_amount_owed` 为累计待缴金额，两者可能不同。
- 例如固定月费 100 元：本期欠费 1 个月时为 100 元；历史 1 个月仍未缴且当前需预付时，累计欠费可能为 200 元。
- 新明细状态 `1000` 为未通知未支付；通知受理后可变为 `3000`，并不表示已支付；`2000` 表示已支付。

原有月度防重判断是“当前账单时间大于执行时刻向前推一个月”，不是按 `YYYY-MM` 唯一键防重。是否改成自然月账期，需要结合客户最终确定的出账日期、补出账和收费规则。

## 复现的问题

| 问题 | 观察结果 | 证据与影响 |
|---|---|---|
| 汇总保存失败后遗留明细 | 先有 1 条明细，汇总为 0 张 | 内存异常注入；真实 HTTP 前注入中断后，也确认明细已提交 |
| 上述失败后重试重复明细 | 重试后 1 张汇总、2 条明细，其中 1 条没有汇总 | **实际本地服务及数据库复现**；两轮临时数据均已清理 |
| 单笔费用失败后无法在当前周期补出 | 两套房只生成 1 条明细；重试被“已经出过账”拦截 | 业务实现逐条捕获异常后仍保存汇总，成功标记掩盖部分失败 |
| 房屋没有业主关系时构造无效明细 | `ownerId=null`、`oweId=1` | 内存中观察到错误报文；真实表的 `owner_id NOT NULL` 会拒绝它，不代表数据库已保存该无效记录 |
| 一次性按月类型 `005` 重复出账 | 顺序执行两次生成 2 张汇总、2 条明细 | 该类型的默认查询起点为当前时刻，配合严格 `>` 查询不能防止重复 |
| 并发月度执行重复出账 | 两个执行者同时通过检查，生成 2 张汇总、2 条明细 | 使用双执行者屏障稳定复现；本地两张表均没有唯一索引兜底 |

另外，在独立连接的临时表上执行实际 Mapper 的 `updateBill`，发现 SQL 仅按 `config_id` 更新，没有限制 `community_id`。当两个小区存在相同收费项标识时，会影响另一小区的当前标记。本地现有数据没有这种跨小区重复标识，因此这是条件性隔离缺口，不作为现有账单已被串改的证据。

## 复现命令

从仓库根目录运行，使用本项目已有 Java 8、已打包的任务服务依赖及独立 MySQL：

```powershell
# 离线：实际业务代码 + 内存服务边界，不连接数据库或微信
python scripts/billing/verify.py

# 实际本地服务：正常月度出账 + 汇总中断与重试；自动清理测试数据
python scripts/billing/verify_local.py

# 独立 MySQL 临时表：Mapper 隔离与支付状态保护，不修改真实账单
python scripts/billing/verify_sql.py

# 原单笔手动推送回归，不发送真实通知
python scripts/tests/run_bill_notify_java.py
```

前三个验证工具返回 `0` 表示全部符合检查条件，`1` 表示验证完成且复现问题，工具错误为 `2`。当前前三条均会因上述已知问题返回 `1`，不能将其描述为全部测试通过。结构化结果只保存在忽略的 `.runtime/billing-audit`，可分享的脱敏快照另存于本文链接的 JSON 文件。

## 后续修复次序

1. 在费用服务内统一提交账单头、明细和当前标记，失败全部回滚；避免跨 HTTP 单独写明细与汇总。
2. 按确认后的账期建立持久防重约束，解决并发、网络中断重试和一次性重复；不要仅依赖 JVM 锁。
3. 校验房屋及业主关系，明确失败记录和补出策略，不以部分成功的汇总阻止补出。
4. 修补当前账单更新的小区条件，补足数据库约束，并在迁移前检查历史重复及孤立记录。
5. 账期确定后，再配置正式生成日、推送日及催缴策略。定时通知应复用手动通知的权限、幂等和不确定结果保护。
6. 模板消息审核通过后，根据正式模板字段接入，并用正式公众号重新验证身份绑定、真实收件及账单链接。

这些是修复建议，不是本轮已经完成的修改。服务精简实验继续暂停。
