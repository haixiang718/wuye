# 简历项目经历：物业收费与微信公众号服务平台

以下内容根据仓库实现、验证记录及实际联调结果整理。项目基于 HC 小区开源系统开展二次开发；个人职责请按本人实际参与及能够独立解释的范围选择。

## 可直接使用的简历版本

**项目名称：物业收费与微信公众号服务平台（开源系统二次开发）**

**项目时间：2026.10—至今**

**项目角色：后端开发 / 全栈开发（按实际情况选择）**
**技术栈：Java 8、Spring Boot、Spring Cloud、OpenFeign、MyBatis、MySQL、Redis、Kafka、Vue 2、uni-app、Node.js、Nginx、微信公众平台、微信支付 API V3**

**项目描述：** 面向物业公司与业主，基于开源物业系统进行业务定制，构建管理后台与公众号 H5 协同的收费平台，支持业主及房产管理、费用录入、账单生成、人工审核、公众号缴费提醒与业主查账，并推进微信在线支付接入。

**主要工作：**

- **收费流程改造：** 梳理费用记录、账单与欠费明细的数据关系，开发手动生成待审核账单及同账期补充出账功能；合并账单审核发布与公众号通知入口，支持通知状态查询及失败重试，避免新增费用遗漏及重复出账。
- **微信身份与房产权限：** 改造为微信公众号 OAuth 直接登录，通过姓名、手机号、身份证号匹配物业预录资料后绑定房产；支持多房产查询及切换，结合 Redis 短期凭据、一次性票据和后端归属校验，限制未绑定用户及跨业主数据访问。
- **支付订单与一致性：** 开发微信支付 API V3 JSAPI 下单、通知验签解密、主动查单及确认关单；通过持久化订单、费用占用、数据库事务和幂等校验处理重复下单、重复通知及支付与关单竞态，使用定时查单补偿通知遗漏，当前处于小额实付联调阶段。
- **服务部署优化：** 将用户、房屋、收费、账户等七个业务模块合并部署，保留原服务调用协议、数据源路由及 Kafka 消费组，支持切回原部署；Java 应用进程由 12 个减至 6 个，同机同流程测试下 Java 工作集约降低 45.3%。
- **存量系统修复：** 定位并修复批量抄表导入、收费字典、人工托收、缴费明细及账单可见性问题；补齐数据库缺失结构，编写带备份、兼容性检查及幂等保护的增量迁移脚本，结合真实 MyBatis SQL、隔离数据库和浏览器流程开展回归验证。
- **公网联调与交付：** 配置 Nginx、HTTPS、业务子域名和 SSH 反向隧道，打通管理后台、公众号 H5、网页授权及消息回调入口；编写本地服务启停、健康检查和备份恢复工具，并整理部署、测试及回退文档。

## 面试介绍（约一分钟）

这个项目是基于开源物业系统做的客户定制，主要解决物业后台出账后，业主通过公众号查看和缴费的问题。我的工作围绕收费流程、业主身份和系统运行成本展开：一方面，把新增费用、生成账单、人工审核、公众号提醒与 H5 查账连接起来，并补上同一期新增费用的补充出账；另一方面，将登录改成微信授权后核验物业登记资料，再绑定房产，所有房屋和账单查询由后端校验归属。运行方面，把七个业务模块合并到一个业务进程中，保留调用协议和数据源边界，Java 应用进程从十二个减少到六个，同机测试工作集降低约百分之四十五。最近完成微信支付 V3 的订单、回调和查单补偿开发，正在进行小额实付联调。

## 成果口径与面试准备

- **来源与职责：** 明确是开源二次开发。不要把已有系统架构和所有原始模块写成个人从零设计；只保留本人能解释实现和取舍的职责。
- **内存指标：** 45.3% 来自 Windows 同机、同构建、相近业务流程预热后的工作集对比，不是 Linux 生产容量结论，也不是并发性能提升。进程数不含 Kafka、ZooKeeper 自身的 JVM。
- **支付状态：** 已完成接口开发及多类回归，已调起微信收银台；真实付款与自动入账尚未完成验收。最近手机报错为支付授权目录未注册，等待商户管理员配置。不能写“完成生产支付闭环”“已稳定收款”。
- **部署状态：** 云服务器承载 HTTPS 和反向隧道入口，业务与数据库仍运行在本机。应写“搭建公网联调环境”，不能写“全部服务生产独立部署”。
- **业务规模：** 没有真实千户运营量、高并发压测或支付金额统计依据，不填写虚构用户数、QPS、可用性或交易规模。
- **建议准备的技术问题：** 费用与账单为何分表、补充账单如何防重、支付回调为何不能直接相信前端结果、关单与付款竞态如何处理、多房产权限如何约束、服务合并如何保持数据源与事务边界、通知失败为何不回滚账单发布。
