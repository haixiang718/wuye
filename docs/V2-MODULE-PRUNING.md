# V2 功能与数据库裁剪

用户于 2026-11-06 确认实施，裁剪和实际数据库迁移现已完成，服务已恢复。V1 固定在标签 `v1.0.0` 和分支 `codex/v1-baseline`；V2 位于 `codex/v2-module-pruning`。

## 裁剪范围

移除报修、投诉、访客、设备管理、门禁、巡检、商城、团购、二手需求和房屋出租的专属页面、接口、任务、Java 类及数据库表。房屋、业主、账户、合同、收费、公众号和停车共享结构按原业务保留。

前端删除 463 个文件；后端删除 1,032 个文件，其中含 975 个主源码 Java 文件、1 个旧商品示例测试、47 个 Mapper。旧 `service-goods` 从构建与启动入口移除。前端和服务端继续拦截退休功能的旧地址。

设备与停车共用的 `machine`、`machine_attrs`、`machine_translate` 及对应 3 张 `business_` 表保留。6 个停车协议接口和业主照片上传保留。“商铺房屋 shops”与“商城 shop”使用不同边界，不能按同一前缀全部阻断。

合同保存中的出租房源回写、旧收费中的报修状态回写，以及报表的报修统计分支已解除。与 V1 比较，212 个保留方法体和 35 条保留报表 SQL 内容一致；实际功能仍以回归结果为依据。

## 数据库迁移

迁移已执行并验证通过，见 [实际执行记录](validation/2026-11-06-v2-database-applied.json)。保留的 313 张业务/共享表内容校验一致，另外 5 张配置表仅有清单中的状态变化。

| 数据库 | V1 表数 | 退休表数 | V2 实际表数 |
| --- | ---: | ---: | ---: |
| TT | 327 | 54 | 273 |
| hc_community | 65 | 20 | 45 |
| 合计 | 392 | 74 | 318 |

精确停用 254 条退休服务、路由、任务和设备事件配置。迁移只改指定配置的状态，其他配置内容及保留表数据通过迁移窗口内的校验验证。

工具 [migrate_v2_pruning.py](../scripts/migrate_v2_pruning.py) 默认仅查看计划；明确表名单在 [v2-retired-tables.json](../scripts/v2-retired-tables.json)。实际修改需要停写、无待确认支付订单、没有其他数据库客户端，并完成完整备份和每张退休表的独立恢复文件。CLI 持有启动器锁，库函数调用方也必须持锁。

```powershell
python scripts/migrate_v2_pruning.py
python scripts/migrate_v2_pruning.py --database hc_community
```

升级已有 V1 实例，应先部署经验证的 V2 代码，在维护窗口对上述两库分别执行工具的 `--apply`。保留工具生成的 `result.json`、完整备份和逆向文件；执行结果不明确或逆向中断时先检查数据库状态，不能重复导入旧全库覆盖现有收费记录。

V1 备份位于本机忽略目录 `.runtime/backups/v1-baseline/`；实际迁移前的新备份和恢复文件位于 `.runtime/backups/v2-pruning/`，不上传 GitHub。只切换 Git 标签不能回退数据库；需要匹配相应的表和配置恢复步骤。

初始化 SQL 已同步裁剪：旧 TT seed 319 → 265，hc seed 65 → 45，减少 33,777,964 字节。与实际库相差的 8 张表由此前业务升级迁移创建，初始化时仍需运行既有升级步骤及 V2 配置迁移。每个保留表块和 SQL 前后导内容均逐字节保留。

## 资源收益与边界

6 个运行 JAR 合计减少 2,264,707 字节，合并 business 包中的项目类由 2,865 减为 2,429。公共依赖库仍占多数包体，不能把源文件减少量等同于内存减少量。

MySQL InnoDB 缓冲池仍为 256 MiB；删表不会自动降低这项设置。Java 进程数仍为 6 个。本轮没有使用相同负载下的 V1/V2 内存对照，因此不宣称节省了具体内存数值。
