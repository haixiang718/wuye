# 业务服务合并试验方案

用户已于 2026-10-24 确认按推荐方案执行。

## 目标和边界

用户要求尝试合并微服务，降低无用的常驻内存开销，不要求适配 2 核 2 GB。本方案以现有已精简的功能范围为基础，目标将默认配置的 12 个 Java 进程减少到 6 个。这里是进程数量目标，实际内存收益必须经过运行测量，不能等同比例推算。

候选合并对象为 user、community、fee、acct、store、common、report，新增统一的 business 启动模块。保留 front、api、order、job、eureka 独立启动。MySQL、Redis、Kafka、ZooKeeper、管理后台 Web、业主 H5 及公众号联调入口继续按原职责运行。

本文件记录设计和只读调查结果，尚未实现、编译或启动合并服务。

## 已核对的代码事实

- 七个候选模块直接依赖同一个 java110-service；common 额外依赖 Activiti。共有约 1685 个 Java 源文件，各模块没有重复的完整类名。
- 去除注释后对组件名和显式控制器前缀的静态扫描未发现跨模块重复；这不能替代 Spring 容器实际启动和接口映射检查。部分 HTTP 路径定义在接口中，仍须运行核验。
- 每个模块原来的启动类分别注册 RestTemplate、业务监听器和 Feign 客户端。不能把所有启动类一起扫描，否则会重复配置。
- 六个业务模块的数据源包含 TT 和 hc_community，默认逻辑数据源为指向 TT 的 ds1；report 只有指向 TT 的 ds0。因此不能直接取 report 配置覆盖其他模块，必须单独核对并生成合并配置。
- 业务监听器统一由 BusinessServiceDataFlowEventPublishing 以静态集合管理。合并后必须一次性扫描所需监听器，并核对业务类型对应的监听器集合，避免重复执行。
- Kafka 消费者使用各业务自己的 topic。合并不删除消息、消费位点或现有主题，不擅自更换消费组。
- 内部接口以 user-service、community-service 等名字通过 Feign 或负载均衡 RestTemplate 调用。进程合并后这些名字仍须正确定位到合并进程，不能只启动新进程就结束原服务。
- 部分内部方法会修改传入 DTO（例如分页参数）。直接用本地 Java 调用替换 HTTP 会失去序列化隔离，可能改变行为；首轮保留内部 HTTP 调用边界。

## 可选方案

| 方案 | 范围 | 取舍 |
| --- | --- | --- |
| 推荐：分阶段合并七个业务模块 | 先验证 user、community，再扩展至七个模块，最终目标 12→6 | 能减少多个 JVM，保留原入口和路由结构，便于定位问题和回退 |
| 只合并 user、community | 目标 12→11 | 变更更小，但节省有限 |
| 全部合为单体并移除服务发现等 | 重构入口、内部调用、事务及消息链路 | 潜在收益更大，改动和回归面显著增加，不作为首轮试验 |

## 推荐实现结构

1. 在专用 codex/ 前缀的 Git 分支开展试验，保留原分布式配置作为回退路径，不覆盖旧模块的启动能力。
2. 增加 service-business 模块，用独立启动类加载候选业务的源码和必要资源。原有各模块的启动类及其 application/dataSource 配置不进入统一扫描，公共类和监听器只初始化一次。common 的工作流资源和相关自动配置需要显式处理。
3. 为合并模式生成独立的本地数据源和应用配置。配置只访问本项目隔离数据库；复用原有映射、事务和数据，不进行业务数据迁移，不重新导入数据库。工作流自动建表行为需要保持与原环境一致。
4. 首轮保留 Feign/HTTP 方式，显式处理本地实现与 Feign 代理的注入选择；旧服务名通过仅在合并模式生效的路由配置指向 business。所有相关调用方采用同一配置，且不能让旧独立实例与合并实例混用同一组业务路由和 Kafka 消费者。
5. 为启动器增加 merged 配置。切换前核对目标 JAR 和配置，停止待替换的业务进程后启动 business，并重启需要刷新路由配置的调用方。保持数据库、Redis 会话和通知记录、消息队列数据不变。原 property/full 配置继续可用。
6. 自动任务继续默认暂停。合并不发送真实微信通知，不发布公众号菜单，不发起支付；公众号授权和通知流程使用现有模拟用例及已保存的测试数据进行回归。

## 验证与验收

- 基线：检查现有启动配置测试及核心查询流程，保存同一环境的内存快照；如果基线本身失败，先区分环境问题，不将其归因于合并。
- 先实现 user、community 的合并容器启动及路由，核对登录、业主、房屋查询，再纳入 fee、acct、store、common、report。
- 构建和配置测试覆盖模式选择、排他启动、原服务名映射、数据源目标、监听器唯一性、失败回退。
- 实际业务验证覆盖后台登录、房屋及业主列表、收费配置、账单及欠费查询、合同、公众号配置、账户和报表查询、业主 H5 房屋和费用查询。保留的停车接口和裁剪边界需要回归。
- 写入回归仅使用明确标记的测试记录，验证保存和查询一致；不对真实用户数据进行试验，不以查询成功代替事务正确性验证。
- 通知回归不调用真实微信发送，支付保持关闭。现有通知去重、状态更新和授权安全测试应继续通过。
- 比较同一查询流程、相近预热状态下 Java 进程数、工作集和私有提交内存，报告实测值和测量口径，不据此承诺生产容量。
- 验收要求包括：合并版本实际可运行、保留功能关键回归通过、分布式版本能回退。若七模块合并遇到未解决冲突，应如实报告已经验证的合并范围，不能宣称目标已完成。

## 风险和回退

主要风险是接口映射或组件重名、Feign 代理选择、数据源/事务差异、监听器重复处理、工作流初始化以及路由缓存未刷新。使用显式扫描和配置解决，不允许通过全局覆盖 Bean 来掩盖冲突。

合并进程故障会同时影响多个业务模块。该取舍适用于当前减少资源开销的目标，但不能把它当作高可用方案。

回退时停止 business，恢复 property 模式及原服务名发现配置，启动原七个业务进程并刷新调用方。数据库和 Redis 无需回滚业务数据；切换过程中保留消息及消费位点。

## 设计自查

范围为业务服务进程合并，未包含登录流程重做、正式公众号切换、在线支付开通或全面单体化。代码调查只是静态可行性依据；12→6 是待验证目标，内存、兼容性和回退均需实际执行后报告。
