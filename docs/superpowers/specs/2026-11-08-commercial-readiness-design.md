# 单家物业、多小区商用完善设计

日期：2026-11-08。用户确认目标为单家物业使用、管理多个小区。基于已确认的渐进完善方向实施，继续保留 V2 裁剪范围。

## 目标及路线选择

采用分阶段完善现有系统：先保障资金可核对和运行可恢复，再统一收费操作和多小区使用体验。整体重写会使现有计费、微信授权、通知和实付证据失效；只改界面无法解决资金与可靠性问题，因此两者不作为本轮路线。

商用完成标准是业务、数据、部署和人工操作都可验收，不能以单笔实付成功或测试数量替代整体验收。

## 当前事实

- 费用自动进入人工审核、拒绝及审核留痕已实现；审核后 H5 展示并进入公众号通知队列。
- 微信 V3 已完成一个指定业主一笔 0.01 元实付和入账核对，仍保持试点开关。
- 云主机是 HTTPS 和隧道入口，业务及数据库仍依赖本机；Linux 包仍限制支付。
- 后台支持小区权限，公众号 H5 当前入口仍有单小区配置限制。后台能管理多个小区不代表 H5 跨小区身份和通知已经验收。
- 最新自动出账依赖数据库触发器；旧运维受限恢复工具拒绝导入触发器，因此旧恢复证据不能代替当前版本完整恢复验收。

## 分阶段验收

| 阶段 | 交付 | 放行证据 |
| --- | --- | --- |
| A 资金核对基础 | 微信日账单只读导入、逐单差异、订单/流水/收据一致性检查、商用差距台账 | 文件解析异常、分单位金额、多项目、重复、跨日、漏入账、身份不匹配的回归及真实本地只读检查 |
| B 部署与恢复 | 当前版本一致构建、支持支付但默认关闭的配置、独立运行、触发器恢复验证、日志轮转及监控 | 目标 Linux 启停/断网/重启验收、数据库和通知队列恢复、回退演练；需要足够资源的业务主机 |
| C 财务闭环 | 对账后台入口及任务、受控退款、异常单处置、费用更正审核、日/月核对 | 权限、幂等、并发、故障恢复、逐笔实付和退款验收；退款由有权人员明确发起 |
| D 多小区与业务体验 | 收费规则、出账日、报表口径、导入预检、H5 跨小区房产与通知、岗位操作手册 | 至少两小区、两微信身份的隔离和跨小区切换实测，物业人员按手册验收 |
| E 正式放行 | 性能与安全回归、真实资料迁移、备份/告警责任、全量支付放行记录 | 客户确认计费口径与角色，资源容量达标，无未处理关键差异，逐项签认 |

## 阶段 A 详细设计

1. 新增独立只读运维工具，不改变现有收费接口、账单、商户设置、支付限额和通知行为。
2. 输入为商户平台导出的原始 ALL 日交易 CSV、北京时间账单日、商户号及 AppID。仅支持明确识别的字段，拒绝残缺文件、错日期、错商户、重复成功交易、非人民币和非法金额。按原订单金额核对，不以扣券后的应结金额或手续费后净额替代。
3. 同商户其他 AppID 行计数说明并排除；退款与撤销记录明确要求人工核查，不据此自动退款、冲正或认为支付正常。
4. 对账以微信交易日为准；匹配文件内全部订单，无论本地下单/入账日期。另查询本地当日已入账订单，缺微信行时标明可能跨日，不能宣称资金丢失。
5. 从现有本地专用数据库读取一致性快照。订单金额以整数分处理，其他金额用 Decimal 精确换算；核对交易号、流水金额、收据金额、明细及账单结清、费用占用。读事务禁止写入。
6. 完整报告仅写入 Git 忽略的 `.runtime/payments/reconciliation/`，控制台只输出计数和结果目录；不读取 OpenID、姓名、手机号、证件号或密钥。输入原始文件不复制到仓库。
7. 输出包含机器可读 JSON 和便于核查的差异 CSV；返回码 0=当前范围无差异，1=需核查差异，2=输入或执行失败。未提供官方日账单不得声称微信对账通过。

## 阶段边界

阶段 A 不自动下载官方账单、不自动修账、不发起退款、不开放全部业主支付、不改变线上部署。CSV 本身没有官方签名验证；文件完整性摘要只用于溯源，账单来源须由财务确认。当前命令只连接本地专用数据库，生产数据库接入另行配置并使用受限账号。

后续按以上阶段继续实施，阶段状态见 `docs/COMMERCIAL-READINESS.md`，不得将规划条目写成已实现。
