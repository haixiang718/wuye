# 账单审核与公众号通知合并

用户已确认收到此前的公众号通知，并明确要求将 H5 账单发布与公众号缴费通知合并。沿用上轮提出的“审核并推送、失败独立重试、避免重复发送”设计，直接实施，不再次确认。

主操作改为“审核并推送”：后台确认一张账单后，先复用原审核事务发布，H5 按原规则立即可查；随后为这张账单的欠费明细建立持久化 Redis 通知任务，由 API 内一个按需处理的后台线程逐条发送。关闭浏览器不会中断任务，API 重启可恢复；不启用旧的定时出账/全小区催缴任务，不新增 Java 进程。

前端继续调用 `POST /app/fee.reviewBill`，新增 `notify:true`；`retryNotifications:true` 仅在用户明确点击“重试失败通知”时提交。未传 notify 的内部兼容调用保留仅审核。审核失败不能建通知任务；审核已成功而任务创建失败时，明确返回已发布及失败原因，可重新操作补建，不回滚审核、不误报全部通知成功。

新增只读 `GET /app/fee.billNotificationStatus`，请求 communityId/billId，仅物业后台 app 可访问并校验有效物业小区关系。统一响应 data 为 `{billId,reviewState,notification:{state,total,processed,accepted,failed,uncertain,skipped,errors,canRetry}}`，通知任务状态 `NONE/QUEUED/RUNNING/COMPLETED/FAILED`；errors 仅含 oweId、msg、retryable，无手机号、OpenID 或密钥。审核发布后允许查看通知状态、明确重试失败项；已发、已支付、不适合通知及结果不确定且不可重试的项不得自动重发。

创建任务的明细 ID 只能来自服务端本小区本账单查询。任务和逐项进度持久保存，初次任务按账单唯一，重复审核或重复提交不能重建或重发；重试仅作用于明确失败且允许重试的明细。已有通知服务继续提供收件人去重、锁、微信受理记录、断网不确定状态和部分收件人恢复。新增首次通知模式，在同一明细发送锁内重新检查已通知状态，防止与手工推送并发导致重复。

页面显示审核/通知进度和错误明细，定时只读刷新当前可见账单的活动任务，离开页面停止轮询。保留欠费清单的逐业主补发入口。大批量通知不在 HTTP 审核请求中同步执行。微信“受理”不描述为“业主已收到”。

验证使用假的微信网络边界与随机隔离账单，禁止向已有真实业主补发。覆盖审核失败、队列失败、重复点击、跨小区权限、批量明细、API 重启恢复、部分失败、状态不确定及重试不重复发送。构建并部署后验证真实后台组合操作和 H5 可见性，清理随机数据并核对原业务数据；用户已收到的 50 元账单只读核对，不重发。商户支付、自动出账继续关闭。
