# 账单流程修复设计

用户在查看全流程诊断报告后要求“修复”，本设计落实已经确认的业务流程，不再次询问相同范围的许可。

## 方案与取舍

采用在现有 Java、MyBatis、管理后台和 H5 内修复的方案。仅修页面无法阻止未审核账单通过接口被查询或支付；把支付另建外部服务会增加部署和凭据管理成本，均不采用。

注册和 H5 属于独立根因修复：匿名公开注册使用服务端默认身份，不采信客户端身份；欠费页只初始化一次，正确处理房屋选择、空结果、加载失败及金额汇总。

账单头增加独立审核发布状态和审核人、时间、意见，默认待审核，旧数据不自动变为已审核。物业员工核对明细后可审核发布，服务端验证小区归属并原子更新；重复审批幂等，业主不可审批。审核与通知状态分离，未发布账单不能推送。业主查询根据已发布账单快照展示应缴金额和账期，不以底层收费项目等同于可支付账单；旧接口也必须受到发布控制。

支付保持未开通状态，修复现有遗留 V2 回调及本地可验证的订单确认边界，不声称完成微信支付商户/V3 接入。回调核对可信支付订单、金额、AppID、商户和签名，完整传递 URL 中公众号标识；失败返回明确失败且保留重试条件，重复回调不能重复记账。持久化记录作为已处理依据，不能以缓存消失推断成功；HTTP 200 还需检查业务结果。对无法证明归属的旧订单安全拒绝，不兼容性放行。

## 验证与边界

先写能复现原问题的测试，再改生产逻辑。Java 定向编译串行执行，所有外发使用替身。实际隔离库集成覆盖注册、后台审批、待审不可见和不可推送、发布后金额账期一致、通知状态、回调重试和防重；仅对随机标识测试资料操作，完成后清理并核对已有数据。

本轮不发送真实微信或短信，不发真实支付订单，不启用自动任务，不改变正式公众号凭据。保留原有未提交的服务号方案与上线计划。完成后重新构建、启动本机服务，更新诊断报告和项目现状，区分代码修复、本地模拟验证和待真实商户验收。
