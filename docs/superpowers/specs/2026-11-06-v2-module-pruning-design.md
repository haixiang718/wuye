# V2 模块与数据库裁剪方案

日期：2026-11-06。状态：依赖预检和 V1 备份完成，待用户确认设计；尚未执行模块删除、删表或运行环境切换。

## 用户目标

将当前可用版本保留为 V1，开始 V2。移除报修、投诉、访客、设备管理、门禁、巡检、商城、团购、二手需求和房屋出租。裁剪完成的条件是剩余功能通过回归验证，不能用表数量减少代替业务验收。

此前已停用的采购、广告等模块维持原状态，本轮不扩大其数据库删除范围。公告、合同、账户、公众号、收费和停车等不因本轮裁剪而被误删或重新启用。工作人员小程序同样核查残留入口，但不新增移动端业务。

## 内存影响的实际含义

表及索引首先占用磁盘。MySQL 的 InnoDB 缓冲池按数据页访问情况缓存，并非为每张表按完整大小常驻分配内存；表定义、打开表缓存等仍有开销。

本次只读查询看到 `innodb_buffer_pool_size=268435456`，即 256 MiB。删掉不用的表不会自动将这个配置降下来，也不代表释放同等大小的进程内存。应同时减少无用的 Spring Bean、Feign 客户端、Mapper、监听器、任务和前端资源，完成后分别比较稳定运行下的进程内存、包大小和查询表现。

11 月 6 日原始盘点中，这批 80 张候选表的数据及索引分配合计约 23.59 MiB，含 112,937 行；这是盘点时的磁盘和行数口径，不是可释放内存估计，也不是最终删表数量。其中门禁申请表 `TT.application_key` 有 112,400 行，不能用“目前不用”代替备份。

## 方案比较

| 方案 | 实施内容 | 收益和限制 |
| --- | --- | --- |
| 仅隐藏入口 | 延续 V1 的页面和接口禁用策略 | 改动小，但业务类、表和部分框架注册仍存在，不能满足这次清理目标 |
| 分层实裁剪，数据库最后迁移（推荐） | 固定 V1，按明确清单移除模块源代码与注册，保留共享依赖；在隔离副本验证后迁移实际数据库 | 能减少运行代码和表，同时以测试和回退控制影响；需要清理交叉依赖 |
| 全面重建为收费单体 | 重写账户、房产、支付和公众号边界 | 调整面大，现有支付与权限链路需要重新证明，不作为本轮目标 |

## V1 保留方式

- V2 工作分支：`codex/v2-module-pruning`。V1 的源代码通过标签/分支恢复，不能用 Git 恢复数据库数据。
- 已用现有备份程序对 `TT` 和 `hc_community` 分别执行完整单事务备份，校验完成标记、表清单、文件大小和 SHA-256。共 327 + 65 张表。
- 备份位于忽略目录 `.runtime/backups/v1-baseline/`；本机索引为 `.runtime/v2-pruning/v1-baseline-backups.json`。不上传业务数据、密钥或本机连接配置。
- 两库分别备份，不宣称跨库同一事务快照。正式迁移时仍需要暂停写入、补做最新备份和保留业务表校验。

## 源代码与运行配置

### 管理后台和 H5

- 移除指定模块的页面、组件、路由注册和专属资源，不能只从菜单隐藏。清除保留页面对已删组件的嵌套引用。
- 后台 `public/js/local-features.js`、H5/员工端的 `config/local-features.js` 和 Java `DisabledFeatures` 保持一致。旧链接和绕过前端的请求继续得到明确的停用响应，不能透传到动态 SQL。
- H5 房产、选项缴费、金额展示、缴费历史和公众号通知深链接保留。仍注册的 `rentingDetail`、`rentingAppointment` 等出租页一并移除。
- 不用字符串包含规则拦截所有 `pay`、`order`、`store` 或 `machine` 路径。停车及业主照片共享接口设精确例外。

### Java 服务

- 延续现有合并服务布局；不恢复原 7 个独立业务进程，也不扩大本轮为再次架构重写。
- 从 API、front、business、job、goods、通用库中清除专属 Controller、BMO、SMO、DAO、监听器、任务、Feign 声明和 Mapper；先形成静态引用清单，再按引用闭包裁剪。
- `service-goods` 已不在默认运行进程中，V2 从有效构建和发行入口移除。仍有用的公司、用户和权限模块保留。
- 共享的启动扫描、监听器发现、订单事务和 Mapper 加载要同步修改，使用 clean 构建，不能靠旧 `target/classes` 混过编译。
- 移除团购、巡检、门禁和报修任务以及专属订阅注册。缴费、公众号通知和支付结果恢复任务保留当前配置，不自动开启账单批量通知，也不扩大实付试点范围。
- Activiti 和 Quartz 表本轮保留；部分合同及共享任务代码仍有引用，不能因删除投诉/巡检就删除整个引擎。

## 数据库迁移约束

1. 默认仅生成计划。删表工具使用逐库、逐表白名单和源结构检查，不能按表名前缀运行通用 DROP。
2. 先在独立随机副本演练裁剪与恢复；检查外键、视图、触发器、存储过程、MyBatis、数据库动态 SQL 和任务/服务注册。当前盘点未发现视图、触发器或存储过程，实际执行前再查。
3. 对已删业务的动态 SQL、服务路由和任务注册按具体 ID/业务编码精确停用或移除；不能从共享配置表中宽泛匹配关键词删除。
4. 业务代码与回归通过后，暂停实际写入，检查待支付/待确认订单，完成最新备份；逐表记录迁移结果，再删除最终清单中的专属表。备份失败或共享依赖未解决立即停止。
5. 所有保留表逐表核对迁移窗口前后的行数和内容校验；收费/支付表另核对金额、订单状态及关联完整性。校验期间保持写入暂停，避免业务变化造成假差异。
6. 回退先停写并判断故障范围；恢复删除的专属表及相关配置，再切回 V1 代码。V2 恢复写入以后禁止直接覆盖整个旧库，否则会丢失新收费记录。

## “剩余功能不受影响”的验收标准

| 保留功能 | 必须验证的行为 |
| --- | --- |
| 后台账号与权限 | 登录、菜单、组织、小区隔离；未授权请求继续被拒绝 |
| 房屋与业主 | 楼栋/单元/房屋查询、新增业主同时绑定多套房屋、原业主资料与头像可读 |
| 微信登录与绑定 | OAuth 有效身份；姓名/手机/证件匹配绑定；未绑定、他人物业和失效会话不能读账单 |
| 费用和账单 | 项目配置、抄表导入、生成费用、生成审核草稿、审核发布、历史账单与金额一致 |
| 通知 | 审核发布与通知任务联动；失败可查询/重试且不重复发送；通知链接进入正确房屋 |
| H5 | 房产与账单查询、分项勾选、金额汇总、缴费历史、切换业主/房屋时不串数据 |
| 支付与入账 | 服务端金额、订单归属、签名及解密验证、重复通知幂等、并发/重复支付、取消/超时恢复、线下收费冲突保护、入账一致 |
| 账户与报表 | 账户明细、收据、员工收费明细及收费时间；旧合同查询继续可用 |
| 停车接口 | 6 个保留协议入口、相关内部查询/状态更新可用；不要求连接真实道闸或新增停车业务 |
| 运行与发行 | clean Java 构建、H5 构建、安装包不携带已删模块专属资源；本地及域名可访问 |

使用临时数据库和受控替身验证新增写入、回调和通知，自动检查不向真实业主发送消息、不发生真实扣款。不把模拟测试说成微信实付复测；若最终需要实付，由用户单独在手机确认。

现有重点验证入口包括 `scripts/tests/run_payment_order_database_java.py`、`run_bill_review_database.py`、`run_owner_history_database.py`、`run_owner_room_creation_java.py`、`run_owner_oauth_java.py`、`run_owner_access_java.py`、`run_bill_publication_workflow_java.py` 和通知测试。共享 `.runtime/billing-audit` 的 Java 执行器串行运行；重构时补充必要的删除依赖和停车边界回归。

## 实施顺序

先固定并验证 V1 → 确认本设计 → 编写逐文件实施计划 → 在代码层解除交叉依赖并裁剪 → clean 构建及业务回归 → 隔离数据库裁剪/恢复演练 → 维护窗口实际迁移 → 恢复服务并验证本地与正式域名 → 提交 V2 验证记录和实际移除清单。

若任一保留链路回归失败，先修复或撤销对应批次，不以裁剪数量为优先目标。只有上述验收通过，才标记 V2 裁剪完成。
