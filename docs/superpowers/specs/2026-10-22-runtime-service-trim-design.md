# 运行服务和空闲资源精简

用户要求减少无用内存占用，明确不要求适配2核2GB。保留此前约定的小区、房屋业主、收费账单、公众号、财务报表、组织权限、合同和停车接口，不额外删除业务。

本轮采用可恢复的启动配置优化。默认 property 配置不启动独立 goods 商品/拼团服务；保留 full 配置及显式启动 goods。其他12个服务仍有保留业务或基础设施依赖，不按模块名称直接关闭。job 保留以提供任务配置和出账能力，定时任务仍默认暂停；启用自动任务时恢复 goods，避免已有拼团任务访问缺失服务。

API 的 Swagger 文档生成通过独立条件配置控制，默认 property 关闭，full 开启；不改变 /api、/app 的业务路由。关闭 JMX、减少 Redis 空闲连接，Druid 使用零初始/最小空闲连接并关闭预编译语句池，保留最大连接数与动态建立连接的能力。full 保留此前参数以便比较和回退。JVM 堆上限不下调。

两种方案比较：仅停止无依赖服务风险小但收益有限；合并微服务可以减少更多 JVM 开销，但需要重构调用、配置及事务，不属于本次用户要求的额外占用清理。

启动器支持 --profile property/full，默认 property；start all 表示当前配置服务集合，显式 goods 仍可启动。新增 trim 动作只停止当前配置排除的已记录进程，不能停止 MySQL、Redis、Kafka、ZooKeeper、业主入口等。restart all 仅重启 Java 和 Web，保留中间件、Redis 通知记录及业主入口。切换配置后现有服务需重启，工具和文档明确说明。

基线恢复时确认现有 Kafka 2.8 在 Windows cleaner 索引重命名处退出，局部兼容配置关闭 Windows 本机 cleaner，不删除数据；Linux 正式部署不应用此项，保留压缩。前后测量均使用相同本机中间件配置。

验收先测配置选择、调度依赖、显式服务、连接池配置与无密钥命令行。实际本机启动 full 获取工作集/私有提交内存快照，再启动 property，按相同查询流程比较；记录 Windows 测量口径和冷启动/缓存差异，不能当作 Linux 生产容量保证。验证后台登录、房屋业主、账单、通知按钮取消及无效明细、报表/停车查询，验证业主房屋和费用查询，不发送真实微信消息，不进行真实支付。
