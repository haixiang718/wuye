# 后台手动生成待审核账单

状态：用户已于 2026-11-04 确认实施。仅生成待审核草稿，审核发布与真实推送留给用户操作。

## 已核实的问题

2026-11-04 新增“测试费用”收费项，固定金额 50 元，已有一笔房屋费用；收费项编号 `922026110445450230`，费用编号 `902026110498670010`。该费用没有 `bill_owe_fee` 明细，收费项也没有 `bill` 汇总记录。关联房屋和已通过的公众号绑定均存在，费用没有丢失。

房屋收费新增操作写入的是 `pay_fee`；审核账单页面读取 `bill`，通知按钮读取其下的 `bill_owe_fee`。现有页面只有审核和欠费清单入口，缺少面向物业员工的手动出账入口。自动任务当前明确关闭，开发者任务页的“启动”是启动定时任务，不是限定单笔的一次执行按钮。

该收费项出账类型为 `005`（一次性费用按月出账）；当前原始数据库的三项出账任务只配置了 `002/003/001`，没有 `005`。因此单纯开启已有按月任务也不能保证生成这笔费用。现有 `GenerateBillProTemplate` 及整批事务已支持 `005`，可以复用，不需要重新定义收费算法。

## 推荐交互

账单管理页增加“生成待审核账单”按钮及收费项目选择区。员工选择当前小区的收费项目后，明确显示“本操作按收费项目汇总符合条件的费用，仅生成待审核账单；审核与推送需要分别操作”。生成完成后刷新账单列表并展示新账单编号和结果；没有可出账明细、已有当期账单、无权限或网络异常均给出明确反馈。

流程：新增房屋费用 → 手动生成待审核账单 → 核对欠费清单 → 人工审核发布 → 按选定业主推送。生成不自动审核，不自动发送通知，不开启自动任务。用户本次的 50 元费用可在功能验证后生成草稿，审核与真实推送留给用户操作。

## 技术范围

1. 仅向原物业后台应用开放 `fee.generateBill` POST 接口，限定当前员工、物业商户和小区管理关系。浏览器仅传小区与收费项 ID，不接受用户提交的金额、业主身份、审核状态或任务配置。
2. API 通过内部 job 服务调用现有生成器，服务端重新查询有效收费项，确认小区归属及支持的出账类型。仅执行所选收费项，复用收费计算、房屋/业主归属查找和 `saveBillSnapshot` 原子事务。
3. 保留原滚动账期及并发防重规则；已有当期账单返回现有账单信息，不覆盖已审核、已推送或已支付账单。同一期新增费用进入已生成账单的补单问题另行设计，不在本轮直接修改已生成快照。
4. 无有效欠费明细时不给出成功的可审核账单；将生成器调整为不保存空账单，并保留原定时入口的兼容性。
5. 不开放 job 内部端口到公网，也不把新管理接口加入业主 H5 网关白名单。

本次不采用“保存费用立即出账”：同收费项可能由员工分批录入，立即出账容易提前锁定不完整的当期批次。也不采用“开启原自动任务”：用户尚未确定正式出账日，且当前任务没有覆盖类型 005。

## 验证与恢复

- 先用失败测试覆盖单小区/单收费项范围、类型 005、原费用计算复用、无欠费不建空单、已有账单防重、越权和接口异常，再实现。
- 隔离测试收费项验证后台按钮生成草稿、金额/明细、重复操作及错误反馈；不对真实业主发送消息，不修改原有已发布账单。
- 构建 API/job 所需模块，备份原 JAR 后重启对应进程；确认后台、公众号 H5、微信回调仍可访问。
- 对本次 50 元费用，只在核实该收费项没有其他应出账费用后，生成一份待审核草稿，供用户自行审核和推送。
- 隔离测试记录按精确来源清理，保留原业务数据；本轮提交与现有未提交抄表修复分开。
