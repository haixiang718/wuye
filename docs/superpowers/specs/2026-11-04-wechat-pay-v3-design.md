# 微信公众号账单支付 V3 接入

用户已确认实施：H5 按已审核账单下单、支付通知验签后自动入账、主动查单补偿，最后手机支付一笔 0.01 元测试账单。

## 已验证的接入条件

- JSAPI 已开通，正式服务号与商户号关联已由用户确认。
- 商户 API 证书和私钥匹配且有效；支付公钥已导入本机私有目录。
- 只读查询随机不存在订单得到 ORDER_NOT_EXIST，商户认证通过，响应公钥 ID 和签名验证通过。
- 密钥只在 Git 忽略的 `.runtime/wechat-pay.json` 与 `.runtime/wechat-pay/`，文档、源码、日志不包含凭据。
- 现有 V2 支付默认关闭；已有持久化订单及事务入账，但缺 V3 接口和公网支付通知入口。

## 方案与范围

采用官方 `wechatpay-java` 0.2.17 SDK 的公钥模式，新增 V3 provider，保留旧 V2 适配器作为关闭状态下的兼容代码。继续采用原系统已发布账单快照与 fee-side 入账事务，不另造收款账本。

其他方案：直接启用旧 V2 可少改下单代码，但缺现有准备的 V3 公钥通知流程；自写 HTTP 签名可减少依赖，但需要承担更多密码学协议实现。本次选择官方 V3 SDK。

本次包含 JSAPI 房屋账单支付、回调验签和解密、前后台查单补偿、确认关单后释放占用、H5 结果确认、正式域名专用支付回调。暂不包含退款、平台账单自动对账、服务商分账、APP/小程序/NATIVE 支付。

## 配置与启用

- Java 通过 `java110.payment.v3.config` 指向本机私有 JSON，另有现有 `java110.payment.enabled` 总开关。
- 配置包括 `enabled`、`notifyUrl`、`pilotUserIds`、`liveForAllOwners`，默认禁用，初次只准测试用户下单。
- 首次实付限制 `pilotMaxTotalFen=1`。可信内部创建接口先核对上限，再创建或复用订单；大于 1 分的真实账单不会因此产生支付占用。正式全量开放需要另行切换 `liveForAllOwners`。
- `SmallWeChat` 仍确定项目与 AppID/商户号的唯一关系；V3 不要求也不使用数据库中的旧 `payPassword`。不能因配置新商户而绕过项目归属校验。
- 在校验配置和部署准备期间，保持收款关闭；通知和查单补记必须能够处理已存在订单，即使新的下单被关闭。

## 支付流程

1. 当前登录用户必须有该房产的有效绑定，服务端重新确认唯一付款 OpenID 和公众号 AppID。
2. 服务端按已发布、未支付、当前账单快照建立持久化 `V3` 订单，只用数据库金额（整数分）。前端提交金额、周期不参与定价。
3. 订单先提交，再向微信 JSAPI 下单。同一待支付账单重复点击复用订单号，超时不释放占用。限定直连 JSAPI，拒绝其他 tradeType。
4. 官方 SDK 签名并验证微信响应，H5 获得 RSA 调起参数和本地订单号。
5. H5 使用 `WeixinJSBridge.getBrandWCPayRequest`，不将支付签名误用为 JS-SDK config 签名。
6. 微信支付专用回调路径为 `/app/payment/v3/notify`（经 `wx.jiaanfuwu.cn` 单独反向代理）。通知不经过访问码或业主登录，但必须由 SDK 校验原始报文签名、公钥 ID、时间戳与 AES-GCM 解密。
7. 校验成功事件、JSAPI 类型、交易状态 SUCCESS、AppID、商户、订单号、币种 CNY、金额、交易号，再调用同一事务入账。只有事务确认为 POSTED 后回调返回成功；入账失败返回可重试错误。
8. 重复回调和主动查单共享现有订单锁与交易号唯一约束，不重复写流水、收据和实收。

## 恢复与关闭

- H5 的成功提示以服务端 POSTED 为准；用户取消、桥接失败仍查一次，不能据此前端结果把订单标成未付或释放占用。
- `/app/payment/v3/query` 与 `/close` 必须登录，按订单持有者匹配后才能访问微信或返回订单状态；响应不包含 payload、OpenID、证书或密钥。
- 后台每分钟有界查单（最多 50 条本商户本 AppID 的 V3 CREATED 订单），覆盖用户关闭页面与通知遗漏。
- 恢复扫描使用 `afterOrderId` 游标，失败订单也推进游标，扫描为空后从头开始，长期未支付订单不能饿死后续到账订单。
- 关单先查单；已支付则入账；未支付才发微信关单并再查到 CLOSED。只有这一证据允许原子标记 CLOSED 和释放费用占用。
- `ORDER_NOT_EXIST`、超时、验签失败不能释放占用。保留异常订单供查单重试。
- `payment_order_item` 改为 `(owe_id,order_id)` 主键，保存关闭前后的历史；活跃占用继续由费用锁和 reservation 表唯一键保护。
- 尚未完成关单或长期未支付的异常订单不会靠 Redis 过期自动清理。

## 验证与交付

- 使用合成证书、RSA 签名、AES-GCM 通知验证官方 SDK、篡改/错误公钥/时间戳/金额/身份等拒绝行为。
- 调用真实入账类的替身测试；MyBatis/JDBC 随机隔离库验证事务、重复回调、关闭/重付、历史和并发约束，不污染业主数据。
- 网关测试证明专用回调不需访问码且不能访问其他支付或内部接口，签名头和原始报文完整转发，支付关闭时仍可回调已存在订单。
- H5 测试确认 bridge 成功而服务端 pending 不会显示已支付，取消后已到账会正常恢复，重试有界，登录身份隔离。
- 构建时使用独立 staging 目录，避免替换正在运行且锁定的 JAR。仅在测试通过后部署，保留旧 JAR 和配置回退。
- 实付验收由用户在手机完成；不替用户支付，不修改真实账单金额为 0.01，不自动发送通知或修改正式应收。
