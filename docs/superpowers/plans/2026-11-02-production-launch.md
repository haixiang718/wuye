# 物业系统正式上线实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将裁剪、合并后的物业后台和业主 H5 部署到正式服务器，先完成绑定、查账与人工通知试运行，再在支付验收通过后开放缴费，最后启用经过核验的自动出账。

**Architecture:** 使用显式 merged 模式，保留六个 Java 应用及现有数据库、中间件。Nginx 提供 HTTPS 和分域入口，业主请求经过正式业主网关；后台入口限制访问。正式服务号、生产数据和运行密钥与本地测试环境分离。

**Tech Stack:** Ubuntu 22.04、Java 8、Spring Boot / Cloud、MySQL、Redis、Kafka / ZooKeeper、Node.js 管理后台、Vue 2 / uni-app H5、Nginx、systemd。

## 二、交付分三步

### 正式微信网关纳入首批部署

按用户提出的“微信网关也接进去”，将正式微信入口作为 A 阶段必交付内容，与 H5、管理后台和 Java 后端一起部署、监控、备份配置及回退。

推荐复用现有 Node 测试网关的已验证协议，独立实现正式运行入口并通过 Nginx 暴露；它是轻量 Node 进程，不增加 Java 应用数量，实际内存占用仍需测量。另一种做法是将入口能力移入现有 Java front，能够减少一个 Node 进程，但涉及重新验证过滤器、会话及转发边界，首期优先采用前者。

| 能力 | 正式接入范围 |
| --- | --- |
| 公众号接入 | 固定回调地址、GET 验签、POST 消息/事件转发；按实际加密模式验证处理 |
| 微信授权 | OAuth 发起及回调路由、同源约束；后端继续负责 state 和一次性票据校验 |
| H5 访问 | 可信客户端身份注入、token 协议转换、业主接口白名单；后端执行数据权限校验 |
| 账单通知 | 后台沿用现有发送业务调用微信接口，网关承接通知后的 H5 跳转访问；不在网关重复生成账单或标记缴费 |
| 微信支付 | 纳入整体上线目标，B 阶段按实际支付接口版本接入下单及独立支付通知入口；商户号未就绪时保持关闭 |

入站链路为“微信/业主手机 → HTTPS/Nginx → 正式业主网关 → front/API → 业务服务”；模板消息是“后台发送业务 → 微信接口”的出站调用，不要求绕行入站网关。

第一批验收包括：真实回调提交成功、所需消息/事件处理成功、正式号授权及票据交换成功、两名业主的数据隔离、通知跳转定位正确、网关重启后会话与发送保护按设计恢复。支付验收另行进行，不能以消息验签成功代替支付通知验证。

本节确定上线范围和推荐架构；正式网关生产代码尚未实施。

| 发布阶段 | 开放给业主的能力 | 进入条件 |
| --- | --- | --- |
| A：小范围试运行 | 正式微信授权、房产绑定、房产及账单查询；有权限时人工推送 | 服务器、备案域名、HTTPS、正式身份隔离及房产业务核验通过；模板通知单独验收 |
| B：在线缴费 | 微信内下单、支付、缴费记录、后台同步、对账 | 商户号与公众号关联完成，支付配置及真实小额支付验收通过 |
| C：每月自动化 | 按约定账期自动生成账单、审核后通知 | 出账故障修复、防重/补账回归、客户账期确认、任务白名单与通知防重验收通过 |

A 阶段付款入口明确显示“暂未开通”，后端也拒绝真实下单。没有模板消息权限时可先开放查询，不能宣称每月通知已可用。

## 四、发布与回退

- 采用版本目录和可切换的 current 指针；每次记录制品摘要、迁移版本和密钥配置版本。旧制品保留。
- 数据库迁移先备份、在恢复副本验证，优先采用前后兼容变更。应用回退必须检查数据库兼容性。
- 首次正式切换前暂停人工及自动出账/通知，短时进入维护页，完成配置、迁移及健康检查后再放行。
- 发现错绑、费用归属异常或支付重复记账时，先关闭相关写入/收款入口，保留回调和流水，核对后修复。
- 不用旧数据库快照直接覆盖已有新订单的生产库；新增支付和账务需保留、核对并补偿。回退代码不等于回退已收款事实。
- Windows 的 `restart all --profile property` 是本地架构回退命令，不是现成的 Linux 发布回退工具。
